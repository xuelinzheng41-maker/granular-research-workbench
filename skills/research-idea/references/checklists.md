# 步骤检查清单（每步做完打勾，缺项不进入下一步）

## 步骤 1 · 选题

- [ ] 比较了至少两条候选（不设上限），记录候选来源及落选理由
- [ ] 用 `falsified` 或原文查过已证伪/已解决题目
- [ ] 能区分研究问题、口径差异和实现偏差

## 步骤 2 · 数学定义

- [ ] 实验型：输入/输出、目标/约束与可计算指标
- [ ] 定理型：对象、量词、假设与命题
- [ ] 没有"我们大概想优化 X"这种模糊表述

## 步骤 3 · 锚点

- [ ] `anchors` 跑出 3~5 篇，tier 1/2 为主
- [ ] 每篇写明「做到哪一步 / 卡在哪」
- [ ] 至少 1 篇是近 2 年的竞品
- [ ] 没有把中文整理稿当锚点

## 步骤 3.5 · 反例检索

- [ ] 用机制关键词跑了 refute.py
- [ ] 命中的负面结果逐条判定类型（直接反例 / 领域限制 / 相关工作）
- [ ] 若有领域级不可能性结果，已避开强主张
- [ ] **阳性对照**：用已知必命中的关键词（如 impossibility/cannot）验证 refute 本身没失灵

## 步骤 3.6 · 最小探针

- [ ] 先写一条决定推进的核心主张，以及竞争解释、对照、继续/停止判据与预算
- [ ] 保留可复核证据，单独说明证据实际支持了什么，不把后续计划当证据
- [ ] 独立复核确认直接支持核心主张才写正式方案；仅支持代理指标或弱命题时暂缓
- [ ] 写清谁会改变哪个决策、阶段资源、里程碑和停止条件

## 步骤 4 · 逻辑链

- [ ] 四段齐全：成因→动机→机制→证据
- [ ] 「成因」有卡片路径支撑
- [ ] 「机制」能用一句话说清与锚点的差异
- [ ] 实验型核查数据/对照/指标；定理型核查引理/边界条件/所需工具

## 步骤 5 · 对抗审查

- [ ] 用了 `templates/reviewer.md`，产出 ≥3 条拒稿理由
- [ ] 每条都有「如何预防」
- [ ] blocker 数 ≤1，否则回步骤 1
- [ ] 没有出现"很有潜力但……"

## 步骤 5.5 · 生死判

- [ ] 定了「哪个实验失败就作废」
- [ ] 正式生死判在主验证之前写定，不拿探针记录冒充预注册
- [ ] 想清楚了不通过时降级成什么产物

## 步骤 6 · 落地

- [ ] mermaid 框架图能看出"挑战→模块→验证"三列
- [ ] 实验排期按 2 核估算，总时长 ≤1 夜
- [ ] 产出在 `ideas/<日期>-<slug>/`，三件套齐全
- [ ] 临时脚本放 `ideas/<日期>-<slug>/scratch/`，**不许写进 runs/**
- [ ] 开头有版本作废表（首次可空）
