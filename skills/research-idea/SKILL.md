# 科研 Idea 生产流程 v1.5

> 核心原则：**没有证据链的想法不是 Idea，是猜测。**
> 每条断言必须能指回一张论文卡、一篇原文，或一次可复算的实验。

**主方向：性能轨道。** Agent 先读论文卡，自己抽组件、自己判断哪些组合值得试；用户只提供时间、算力、数据约束，不提供组合方向。只有目标是定义/定理审计时才走 audit 模式。性能候选按 [性能轨道](references/performance-track.md) 和 [Agent 主导的组件重组](references/component-recombination.md) 执行，必须有两个基础方法、两个互补组件、强基线、naive 拼接、消融和 kill_if。

## 0. 前置检查

第一次使用按 [快速上手](README.md) 配置独立工作目录，并运行 `python scripts/selftest.py`。接入现有知识库时，再运行 `python scripts/kb.py doctor` 和 `python scripts/selftest.py --with-kb`。无库时直接用可核对的原文、公开数据或数学构造。第三方复验见 [独立验收指南](VALIDATION.zh.md)。

## 1. 三层结构（这是"可复用"的关键）

| 层 | 文件 | 换方向时要改吗 |
|---|---|---|
| 流程层 | `SKILL.md`（本文件） | ❌ 不改 |
| 领域层 | `references/domain-<方向>.md` | ✅ 换方向 = 换这个文件 |
| 工具层 | `scripts/kb.py` | ❌ 不改（靠环境变量适配） |

先按下表选理论型或实验型；有自己的知识库时再配置领域层。

### 换一个研究方向，30 分钟适配

```bash
# 1) 新建领域文件（复制现有模板改内容）
cp references/domain-template.md references/domain-my-topic.md

# 2) 指向新的知识库与数据集（不写死路径）
export LAB_KB="$PWD/kb"
export LAB_DATA="$PWD/datasets/parquet"
export LAB_IDEAS="$PWD/ideas"
python scripts/kb.py doctor
python scripts/kb.py stats
```

**流程不变、清单不变、脚本不变**——只换数据与领域知识。

### 选哪个领域文件（按研究类型，不按学科）

| 你的研究类型 | 用哪个 |
|---|---|
| 定理型（证明为主：界、构造、不可能性） | `references/domain-theory-math.md` |
| 实验型（方法 + benchmark） | `references/domain-experimental-cs.md` |
| 组内专用领域 | 使用组内另行提供的领域文件和知识库 |
| 其他方向 | `references/domain-template.md` |

**无库模式**：文献步骤用可核对的 DOI、arXiv 或其他权威标识；记录反例检索词和覆盖范围，评分用 `--external`。探针及正式落地流程相同。

## 2. 六步流程

每步做完对照 `references/checklists.md` 打勾，缺项不进下一步。

### 步骤 1 · 从多来源生成候选

```bash
kb.py gaps --section A --limit 20      # A=无人做 B=没解决 C=已解决
kb.py stats                            # 哪个族群拥挤
kb.py falsified                        # 是否已被证伪（有 85-先前结论 时）
```

先问清研究者本周可用时间、每个小探针预算、实际技能和可用资源。参考 [候选输入示例](examples/brief.json) 比较至少两条候选（不设上限），覆盖文献空位、反常、跨域迁移中的至少两类。每条候选写一句可反驳主张、最近工作及实际差异、最大风险和可执行的最小验证。不足两种可靠来源时，记录缺口并暂停比较，不编造来源。

如果目标是“新算法/组合优化后效果更好”，不要把审计 gap 当主线；改用 [性能轨道](references/performance-track.md) 和 [性能 brief 示例](examples/performance-brief.json)。每条候选必须写清两个基础方法、两个互补组件、集成点、预期增益、至少两个基线、数据集、指标、消融和 kill_if；先做 3 数据集 × 3 seeds 的 pilot，过门才进完整实验。性能轨道只验证声明字段，不证明增益真实。

运行 `python scripts/shortlist.py <比较记录.json>` 检查资源和记录。未核实文献、已有反例或明显超预算的候选应暂缓；都不合格时不推荐。`no_overlap_retrieved` 只表示在已记录的检索范围内未找到直接重合，不证明新颖。只有研究者选定可做的候选，才创建探针。GitHub 只作为可复核实现或失败案例的来源。

### 步骤 2 · 用数学语言定义任务

实验型写输入/输出、目标/约束和可计算指标；定理型写对象、量词、假设及目标命题。两类都写清什么证据会推翻当前主张。

### 步骤 3 · 建文献坐标系（3~5 篇锚点）

```bash
kb.py anchors "关键词1 关键词2" --n 5
kb.py show "卡片名" | head -80
```

优先级：tier 1/2 真论文（自动排除整理稿）→ 同方法族 → 一篇竞品/一篇奠基/一篇可借鉴。
每篇必须能说清「做到哪、卡在哪」，卡点就是切入点。

### 步骤 3.5 · 反例检索（必做）

写逻辑链之前，先用机制关键词查全文语料：

```bash
python scripts/refute.py stability granularity
```

命中不是让你放弃，是让你**缩小主张**：

| 命中类型 | 处理 |
|---|---|
| 该方法的直接反例 | idea 作废，回步骤 1 |
| 领域级不可能性结果 | 保留 idea，但只主张可测的下游收益，不主张「选出正确解」 |
| 相关工作的一般否定结论 | 在锚点里引用，作为边界条件 |

无库时直接检索原文、反例和同义机制，并记录检索范围。没有命中不是没有反例。

### 步骤 3.6 · 最小探针（新候选必做）

用 `kb.py draft <短名>` 创建候选，先写一条决定推进的核心主张，再做受控实验、小构造或关键引理。作者写明探针实际支持的主张。`probe.py review-input` 默认只给首轮材料：冻结主张、复验条件、证据引用和复核摘要，不含作者判定、支持陈述、观察、局限和后续建议；复核者先独立核查原始证据、对照和最强替代解释并记录判断，再决定是否加 `--full` 查看完整记录。复核记录须声明 `reviewer_type` 与 `author_result_exposure`（自我声明，不验证身份；缺字段按 `unspecified` 处理，不当作盲审）。只有证据直接支持核心主张（`direct`）的候选才能推进。只验证代理指标或弱命题就暂缓；缩小主张后须重新复核。见 `references/probe-first.md`。

### 步骤 4 · 还原科学逻辑链

```
问题成因 → 解决动机 → 创新机制 → 预期证据
```

预期证据要写成可执行实验（数据/对照/指标）或可审查的证明路线（关键引理/边界/所需工具），并区分探针初证和后续验证。

```bash
kb.py feasibility "锚点卡片名"    # 数据集在不在本地
```

### 步骤 5 · 对抗审查

读 `templates/reviewer.md`，扮演顶刊审稿人：≥3 条具体拒稿理由 + 每条处方。
**3 条里 2 条补不上 → 不合格，回步骤 1。**

禁止「很有潜力，但可以考虑……」这类和稀泥结论。

### 步骤 6 · 框架图 + 落地

```bash
kb.py scaffold <候选ID>       # 用 draft 输出的带日期 ID；检查通过才生成三件套
```

mermaid 画三列：研究挑战 → 方法/引理 → 验证。写清谁会用结果改变什么决策、现有资源、1–2 周里程碑及最大阻塞。实验首轮按服务器实际资源估算。

## 3. 硬规则

0. **反例检索未做，或探针没有通过独立复核，不许进入正式写作。作者的 advance 仅是建议。**
1. 每条断言标来源；没来源的句子删掉（规范见 `references/evidence-standards.md`）
2. 不编论文：不确定就 `search`，查不到就说"库内没有"
3. 实验型的数据集必须真实可用，缺的要么替换要么写明需求；定理型不得拿有限枚举代替证明。
4. 区分 A/B/C 类空位；B 类要说明"别人为什么没解决"
5. **必须定生死判**：主实验或正式证明前写清什么结果使主张作废；探针计划不等于正式预注册。
6. **临时脚本放 `ideas/<slug>/scratch/`**，不许污染 `runs/`
7. 不写"显著提升"，写数字或"预期 X 个点，待验证"
8. **改动 scripts/ 后先跑 `scripts/selftest.py`，全绿再提交。**
9. 文档开头放**版本作废表**，旧主张和负面结果保留。

## 4. 常见失败模式

| 症状 | 病因 | 处方 |
|---|---|---|
| Idea 变成模块堆砌 | 跳过步骤 1/4 | 回空位表，先说清谁的哪步卡住 |
| 实验设计不出来 | 步骤 2 没写指标 | 补指标，且必须现有数据能算 |
| 被批 novelty 不足 | 锚点缺近期竞品 | 补 tier1 竞品，明确差异 |
| 做完发现别人做过 | 没扫 C 类 | 先 `gaps --section C` |
| 反复想同一个方向 | 没查已证伪清单 | 每次开工先 `falsified` |

## 5. 产出规范

```
ideas/<日期>-<短名>/
├── probe-plan.json / probe-result.json  核心主张与作者判定
├── probe-review.json  独立复核、所审材料摘要及复核者声明
├── evidence/     可复核的读数、命令或数学推导
├── idea.md        数学定义 / 锚点 / 逻辑链 / 排期 / 框架图 / 风险
├── anchors.md     锚点清单 + 每篇「做到哪、卡在哪」
└── review.md      对抗审查（≥3 条拒稿理由 + 处方）
```
